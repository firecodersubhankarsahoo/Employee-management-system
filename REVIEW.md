# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health` (lines 72-74) | Unconditionally returns `{"status": "ok"}` without verifying database connectivity. The specification explicitly requires returning 200 only when MongoDB answers a ping, else 503. | Stopping MongoDB and calling `GET /health` returns 200 instead of 503 Service Unavailable. | Wrapped `db.command("ping")` in a try/except block; raised `HTTPException(503, "Database unavailable")` if the ping fails. |
| 2 | `compute_late_minutes` (lines 33-38) | Timezone mismatch: Replaces `punch_in` hour and minute directly with `shift_start` values without converting to IST or anchoring to the shift's calendar date. Because `punch_in` is in UTC, replacing its hours with IST numbers compares UTC to IST directly (producing ~5.5-hour skew). | Shift start `09:30` IST with punch-in `09:35` IST (`04:05` UTC). `start` becomes `09:30` UTC, giving a difference of `-5 hours 25 minutes`, incorrectly returning 0 late minutes. | Converted `punch_in` to IST (`Asia/Kolkata` / UTC+05:30), constructed `shift_start` on the shift date in IST, and computed the delta cleanly. |
| 3 | `compute_late_minutes` (lines 33-38) | Grace period boundary violation (R2): R2 requires late minutes when punch-in is *strictly more than* 10:00 after shift start, then floor minutes from `shift_start`. Line 37 checks `minutes > 10` where `minutes = int((punch_in - start).total_seconds() / 60)`. For `09:40:01` (601 seconds), `int(601/60)` is 10, so `10 > 10` evaluates to False, incorrectly returning 0 instead of 10. | A punch-in at `09:40:01` for a `09:30` shift returns 0 instead of 10 late minutes as specified by R2. | Checked `diff_seconds > 600`. If True, compute floor minutes elapsed since shift start (`int(diff_seconds // 60)`). |
| 4 | `compute_late_minutes` (lines 33-38) | Overnight shift handling: On overnight shifts (e.g., 22:00-06:00), a punch-in after midnight (e.g., 01:15 IST) belongs to the shift that started the previous day (R1). The starter replaces the hour on the punch-in calendar date, anchoring to 22:00 later that night. | Punch-in at `01:15` IST on an overnight shift yields a negative time difference instead of elapsed minutes since yesterday's 22:00 shift start. | Anchored `shift_start` to the attendance date (which is yesterday for post-midnight punches before shift end per R1). |
| 5 | `compute_work_hours` (lines 40-42) | Uses Python's built-in `round()`, which applies round-half-to-even (banker's rounding). R4 explicitly requires rounding to 2 decimal places half-up (e.g., 8.125 must round to 8.13). | Any duration where the third decimal digit is 5 and the second is even (e.g., 2.555 -> 2.55 instead of 2.56, or 8.125 -> 8.12 instead of 8.13). | Replaced with `decimal.Decimal` and `ROUND_HALF_UP` (`Decimal(str(raw_hours)).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`). |
| 6 | `compute_overtime` (lines 44-48) | Ignores the 30-minute minimum threshold (R3). The starter returns `max(0, int(diff / 60))`, awarding overtime for any positive duration (e.g., 5 or 15 minutes). | Punching out at `18:35` for an `18:30` shift returns 5 overtime minutes instead of 0. | Added the condition `minutes >= 30` per R3; if under 30 minutes, returns 0. |
| 7 | `compute_overtime` (lines 44-48) | Broken overnight shift end date: Line 46 parses `date_str` and replaces hour/minute with `shift_end`. For overnight shifts (`shift_end <= shift_start`), `shift_end` occurs on the *next* calendar day. | Overnight shift 22:00-06:00 on date `2026-07-06`: punch-out at 06:40 on July 7 is compared against 06:00 on July 6 (24 hours in the past), calculating ~1500 overtime minutes instead of 40. | For overnight shifts, added 1 day (`timedelta(days=1)`) to the base attendance date when constructing `shift_end`. |
| 8 | `POST /employees` (lines 78-85) | Race condition on duplicate `emp_code`: Relies solely on an application-level `find_one` check followed by `insert_one`. Without a unique index, two concurrent requests with identical `emp_code` both pass the check and insert duplicates. | Concurrent execution of two identical employee creation requests results in duplicate records or inconsistent states. | Added an idempotent unique index on `emp_code` at startup and catch `pymongo.errors.DuplicateKeyError` to return a 409 Conflict. |
| 9 | `POST /employees` (line 82) | Server creation time uses `datetime.now()` (naive local machine time). Must be stored as UTC BSON date and serialized as integer epoch milliseconds in the HTTP API response. | Calling `POST /employees` returns an ISO string or datetime object instead of epoch milliseconds, violating `openapi.yaml`. | Used `datetime.now(timezone.utc)` for MongoDB storage and converted to epoch milliseconds in the API response. |
| 10 | `EmployeeIn` model (lines 53-61) | Missing contract validation: Does not validate `emp_code` format (`^EMP\d{4,6}$`), email format, name/department lengths, or check that `shift_start != shift_end` (which requires 422 per OpenAPI). | Sending `{"emp_code": "INVALID", "shift_start": "09:00", "shift_end": "09:00"}` succeeds with 201 instead of 422. | Added regex and field validators in Pydantic models matching the OpenAPI schema, including a model validator enforcing `shift_start != shift_end`. |
| 11 | `list_employees` (line 93) | Pagination calculation off-by-one: Computes `skip = page * page_size`. For `page=1, page_size=20`, `skip` evaluates to 20, skipping the entire first page of results. | Querying `GET /employees?page=1` omits the first 20 employees. | Corrected the formula to `skip = (page - 1) * page_size`. |
| 12 | `list_employees` (lines 94-95) | `total` ignores query filter: Computes `total = db.employees.count_documents({})`, returning the total collection size rather than the filtered count. Also missing the required sort order (`emp_code` ascending). | Querying `GET /employees?department=Sales` reports `total` for all departments combined instead of matching Sales employees. | Updated to `count_documents(q)` and chained `.sort("emp_code", 1)` to the cursor. |
| 13 | `punch_in` (lines 100-101) | Unhandled 500 error on unknown employee: Queries `emp = db.employees.find_one(...)`. If `emp` is None, line 113 accesses `emp["shift_start"]`, triggering an unhandled `TypeError` (500). | Calling `POST /attendance/punch-in` with a non-existent `emp_code` returns 500 Internal Server Error instead of 404 Not Found. | Added an explicit check: if `emp is None`, raise `HTTPException(404, "Employee not found")`. |
| 14 | `punch_in` (lines 102-103) | Incorrect attendance date derivation (R1): Computes `d = ts.date().isoformat()`. If `ts` is in UTC, `ts.date()` yields the UTC date instead of the IST calendar date. Also fails to apply the overnight rule (punches before `shift_end` belong to yesterday). | Punch-in at `2026-07-06 21:55 IST` (`16:25 UTC`) assigns the record to `2026-07-06` by luck, but punch-in at `00:30 IST` on July 7 for a 22:00 shift incorrectly assigns date `2026-07-07` instead of `2026-07-06`. | Converted `punch_in` to IST and applied R1 overnight rules to derive `date`. |
| 15 | `punch_in` (lines 104-105) | Concurrency race condition on duplicate punch-in: Uses `find_one` then `insert_one`. Under concurrency, two simultaneous requests for the same employee and date both pass and create duplicate records. | Firing concurrent punch-in requests produces multiple records for the same employee on the same date. | Enforced a compound unique index on `("emp_code", "date")` at startup, and catch `DuplicateKeyError` to return 409 Conflict. |
| 16 | `punch_in` (lines 106-121) | Invalid status and missing instant validation: Allows arbitrary status strings instead of restricting to `PRESENT`, `WFH`, `ON_DUTY`. Does not validate epoch milliseconds bounds or truncate to whole seconds (R1). | 18 | `list_attendance` (lines 127-150) | Missing date range validation and incorrect response contract: Does not validate `date_from > date_to` (must return 422 per OpenAPI). Exposes internal `id` and fails to convert BSON datetimes to epoch milliseconds. | Passing `?date_from=2026-07-10&date_to=2026-07-01` returns 200 with an empty list instead of 422 Unprocessable Entity. Response items contain `"id"` instead of contract schema. | Added date validation (`422` if `date_from > date_to`) and transformed response documents to serialize datetimes to epoch milliseconds without MongoDB `_id`. |

Also note anything you looked at and decided was **not** a defect, and why:

1. `IST = timezone(timedelta(hours=5, minutes=30))` (line 25): Confirmed correct. Indian Standard Time is UTC+05:30 with no daylight saving time transitions, so a fixed offset is accurate year-round.
2. Identifying employees by `emp_code` rather than MongoDB `_id`: Confirmed correct. Per `openapi.yaml` and `DATA_MODEL.md`, `emp_code` is the business identifier assigned by HR and MongoDB `_id` is purely internal and must never be exposed or accepted.
3. Addressing attendance records by natural key `(emp_code, date)`: Confirmed correct. Attendance records do not have an ID; each document is uniquely identified by the combination of employee code and attendance calendar date.
4. Using PyMongo synchronous driver rather than Motor: Confirmed correct. FastAPI runs standard synchronous path functions in an `anyio` worker threadpool, which provides clean, robust, and performant execution for database drivers when backed by proper indexes without mixing async paradigms.
